# 巨型单文件重构方案

> 创建日期：2026-08-26
> 适用版本：v0.1.3（commit c2a1546）
> 性质：纯结构性重构方案——只移动代码、不改行为，为后续云同步功能铺路

---

## 1. 现状评估

### 1.1 四个巨型文件

| 文件 | 行数 | 体积 | 承担的职责 |
|---|---|---|---|
| `src-tauri/src/main.rs` | 1397 | 58 KB | 约 50 个 Tauri 命令 + 窗口管理 + 同步预埋 + 应用装配 |
| `src-tauri/src/db.rs` | 1146 | 44 KB | 全部 SQLite 操作 + 建表 + 数据库迁移 |
| `src/App.tsx` | 1194 | 48 KB | 管理台主窗口的全部 UI 与交互逻辑 |
| `src/NoteApp.tsx` | 805 | 32 KB | 便签悬浮窗的全部 UI 与交互逻辑 |
| （附带）`src/App.css` | 2170 | 37 KB | 管理台全部样式，同样偏大 |

### 1.2 各文件内部结构剖析

**`main.rs`（1397 行）混装了五类职责：**

1. **领域命令**（约 50 个 `#[tauri::command]`）：
   - 分类：`get_categories` / `add_category` / `delete_category` / `rename_category` / `reorder_categories`
   - 便签：`get_notes` / `get_note` / `add_note` / `save_capture` / `update_note` / `set_note_pinned` / `set_note_color` / `set_note_style` / `set_note_category` / `duplicate_note` / `reorder_notes` / `discard_empty_note`
   - 回收站：`delete_note` / `restore_note` / `delete_note_forever` / `auto_clean_trash`
   - 待办：`get_all_todos` / `add_todo` / `update_todo` / `delete_todo`
   - 时间轴：`get_all_timeline`
   - 附件：`get_attachments` / `pick_attachment` / `add_attachment_path` / `delete_attachment` / `open_attachment`
   - 导出：`export_note` / `export_all`
   - 隐私：`get_privacy_status` / `set_privacy_password` / `verify_privacy_password` / `change_privacy_password` / `reset_privacy_password`
   - 快捷键与捕捉：`get_shortcuts` / `set_shortcut` / `show_capture`
   - 窗口：`open_note` / `close_note_window` / `get_open_note_ids`
2. **窗口构建辅助**：`create_note_window`、`centered_position`、`top_center_position`
3. **同步预埋**：`queue_change`、`mark_unsynced`、`snapshot_json`——注意这三者说明云同步已在路上，届时同步模块还要往这个文件里塞代码
4. **时间轴记录辅助**：`log_timeline_in`
5. **应用装配**：`main()` 里的插件注册、状态注入、`generate_handler!` 命令清单

**`db.rs`（1146 行）的结构：**

- `init_db` + `migrate`（116–326 行）：建表与迁移，含 `categories_new` 重建等高风险逻辑
- 五个领域的 CRUD：categories / notes（含回收站状态机）/ todos / timeline / attachments
- 工具函数：`new_uuid`、`hash_password`

**`App.tsx`（1194 行）：**

- 单组件内 **28 个 `useState`**（38–83 行）：笔记、分类、待办、时间轴、视图、搜索、排序、右键菜单、颜色选择器、拖拽状态、隐私状态……全部平铺在 `App` 组件顶层
- 10 个 `useEffect`、20+ 处散落的 `invoke` 调用（233–1177 行），数据获取、命令调用、错误处理混在 JSX 事件回调里
- 分类拖拽排序、重命名、右键菜单锚定（含底部锚定逻辑）等复杂交互全部内联

**`NoteApp.tsx`（805 行）：**

- 纯工具函数与组件混写：`parseColor`、`cssVar`、`noteBackground`、`fmtSize`、`fileIcon`、URL/邮箱正则（26–73 行）
- 窗口拖拽、缩放、展开/收起、300ms 防抖保存、待办、附件、样式切换、右键菜单全部在一个组件里

### 1.3 不重构的实际代价

1. **云同步功能无处落脚**：`LOGIN_SYNC_SPEC.md` 已设计完成（待实现）。同步要同时触碰命令层、数据库层、前端状态层，按现状所有改动都会砸进这 4 个文件，diff 巨大、review 困难、与并行修复冲突概率高。
2. **改一处怕崩全局**：`App.tsx` 里 28 个状态相互交织，改右键菜单逻辑时可能意外影响拖拽排序。
3. **开发体验劣化**：IDE 打开千行级文件明显卡顿；Vite HMR 在 `App.tsx` 每次改动都要重新执行整个组件模块。

## 2. 重构原则（红线）

1. **只移动，不改写**：函数体原样搬迁，不顺手"优化"逻辑。任何行为变更都留到重构完成后的独立提交。
2. **IPC 契约冻结**：所有 `#[tauri::command]` 的命令名、参数名、返回类型保持逐字节不变，前端 `invoke` 调用零改动。
3. **数据库契约冻结**：表结构、`migrate` 逻辑、字段名不动，保证用户现有 SQLite 数据无缝兼容。
4. **小步提交**：每个模块迁移独立成一次 commit，提交信息沿用现有 `refactor:` 前缀习惯，任意一步可单独回滚。
5. **基线先行**：动手前先建立回归基线（见第 5.0 节），没有基线不开工。

## 4. 从哪里改：五阶段执行计划

**推荐路线：后端先行。** 理由有二：① 云同步是下一个主线功能，后端先拆好，同步代码直接落进 `change_tracking.rs` / `commands/` 新结构；② `db.rs` 全是纯函数，是整个项目里最容易验证、风险最低的起点，适合作为第一步建立信心。

### 阶段 0：建立基线（前置，不可跳过）

1. 备份当前用户数据目录下的 SQLite 文件一份。
2. 导出两份"契约清单"存档（具体命令见 5.2 节）：全部已注册命令名清单、前端全部 `invoke` 调用清单。
3. 走一遍第 5.4 节回归清单，确认当前版本全部功能正常，作为对照基准。

### 阶段 1：拆 `db.rs` → `db/` 模块

**做什么**：建 `db/` 目录，按 3.1 的结构把函数原样搬入对应文件；`db/mod.rs` 里保留所有 `pub struct` 类型定义并 `pub use` 重新导出。

**关键约束**：`main.rs` 中所有 `db::xxx` 调用点不改——只要 `mod.rs` 的 re-export 完整，调用方零改动。

**风险**：最低。纯函数搬移，编译器兜底。

**验证**：`cargo check` 通过 + 5.2 契约比对 + 启动应用确认数据正常加载。

### 阶段 2：拆 `main.rs` → `commands/` 模块

**做什么**：
1. 先抽 `state.rs`、`windows.rs`、`change_tracking.rs`、`note_factory.rs`（辅助函数层）。
2. 再按领域抽 `commands/*.rs`，每个命令函数连同其 `#[tauri::command]` 属性原样搬移。
3. `main.rs` 的 `generate_handler!` 清单改为引用各模块路径，**清单内容本身一个命令不增不减**。

**关键约束**：命令签名逐字节不变；`generate_handler!` 前后各导出一次做 diff，必须完全一致。

**风险**：低。个别命令依赖 `AppState` / `AppHandle`，import 路径调整即可，编译器全兜底。

**验证**：`cargo check` + `cargo clippy` + 5.2 契约比对 + 完整回归清单。

### 阶段 3：抽 `NoteApp.tsx` 的纯函数与保存逻辑

**做什么**：
1. 26–73 行的纯函数搬入 `src/lib/noteUtils.ts`（唯一允许顺手做的事：给这些纯函数补单元测试，见 5.5）。
2. 防抖保存相关的 state 与 effect 抽成 `src/hooks/useNoteSave.ts`。

**风险**：中低。防抖保存涉及定时器与组件卸载时序，需要重点回归"编辑→快速关窗"路径。

**验证**：`tsc -b` 通过 + 便签窗口回归清单（5.4 节第二部分）全走一遍。

### 阶段 4：组件化 `NoteApp.tsx`

**做什么**：把右键菜单、样式菜单、附件列表抽成 `components/note/` 下的子组件；`NoteApp.tsx` 保留窗口级状态（展开态、拖拽、缩放）作为组合层。

**风险**：中。便签窗口的拖拽排除区（`DRAG_EXCLUDE`）、收起/展开态与子组件有交互，抽离时 props 边界要设计清楚。

**验证**：便签窗口回归清单全走 + 重点验证拖拽、缩放、收起态滚动。

### 阶段 5：拆 `App.tsx`（最后做，最复杂）

**做什么**：
1. 第一步抽 `api/notesApi.ts`：把 20+ 处散落的 `invoke` 收敛成带统一错误处理的方法，`App.tsx` 里不再直接出现 `invoke`。
2. 第二步抽子组件：`ManagerSidebar` → `NotesGrid`/`NoteCard` → `NotesContextMenu` → `ManagerHeader`，一次只抽一个，每次抽完走一遍管理台回归。
3. 状态分配原则：**状态下沉**——`contextMenu`、`colorPicker`、`sortMenuOpen` 这类局部交互状态下放到使用它的子组件；`notes`、`categories`、`view` 这类全局状态留在 `App.tsx`。

**风险**：最高。28 个状态相互交织，抽组件时容易出现状态提升不当导致的行为漂移（如右键菜单关闭时机、拖拽排序的临时状态）。

**验证**：管理台回归清单全走 + 每个子组件抽离单独 commit，出问题可精确回滚某一步。

## 5. 如何验证改得对不对

### 5.0 验证总策略

重构正确性 = **编译通过** + **契约不变** + **数据兼容** + **行为回归**。四层全过才算一个阶段完成。

### 5.1 静态验证（每步必做）

| 检查 | 命令 | 说明 |
|---|---|---|
| 前端类型 | `npm run build`（含 `tsc -b`） | 类型错误零容忍 |
| 前端 lint | `npm run lint`（oxlint） | |
| Rust 编译 | `cargo check`（在 `src-tauri` 下） | |
| Rust 静态分析 | `cargo clippy` | 搬移过程中意外引入的警告 |
| 完整构建 | `npm run tauri build`（每阶段末一次） | 确认打包链路不坏 |

### 5.2 契约验证（防 IPC 漂移的核心手段）

重构前先导出基线，每个阶段后重跑比对，**输出必须与基线完全一致**：

```powershell
# 基线 1：后端注册的全部命令（generate_handler! 清单）
Select-String -Path "src-tauri\src\main.rs" -Pattern "^\s+(\w+)," |
  ForEach-Object { $_.Matches[0].Groups[1].Value } | Sort-Object > baseline_commands.txt

# 基线 2：前端全部 invoke 调用点
Select-String -Path "src\*.tsx","src\*.ts" -Pattern "invoke\('([^']+)'" |
  ForEach-Object { $_.Matches[0].Groups[1].Value } | Sort-Object -Unique > baseline_invokes.txt
```

阶段 2 完成后重跑（路径改为新模块），用 `Compare-Object` 比对：

```powershell
Compare-Object (Get-Content baseline_commands.txt) (Get-Content new_commands.txt)
# 无任何输出 = 契约未漂移
```

### 5.3 数据兼容性验证

`db.rs` 的 `migrate` 涉及表重建，是最需要盯的地方：

1. 用阶段 0 备份的 SQLite 文件，在重构后的版本启动应用，确认：便签、分类、待办、时间轴、附件全部正常显示。
2. 连续启动应用两次，验证 `migrate` 幂等（第二次启动不应再触发迁移动作）。
3. 对比重构前后数据库文件的表结构（`sqlite_master`），必须一致。

### 5.5 借重构补测试（投入产出最高的部分)

项目目前零测试。重构本身不引入测试债务，但拆出来的纯函数是天然的测试目标，建议顺手补：

**Rust 侧（最高价值，`cargo test` 原生支持，零新增依赖）**——用内存数据库 `Connection::open_in_memory()`：

- `migrate` 幂等性：连续执行两遍，表结构与数据一致
- 便签状态机：`trash_note` → `restore_note` 回到 active；`trash_note` → `permanently_delete_note` 不可恢复
- `reorder_notes` / `reorder_categories`：乱序输入后顺序正确持久化
- `duplicate_note`：副本字段完整、是新 uuid
- `hash_password`：相同盐+密码输出稳定

**前端侧（中等价值，需引入 `vitest`）**：

- `parseColor` / `noteBackground`：各种颜色与透明度组合
- 排序逻辑：四种排序模式的纯函数版本

如果不想引入前端测试框架，至少保证 `lib/noteUtils.ts` 的纯函数被 5.4 清单覆盖。

### 5.6 Git 策略

- 每阶段一个（或几个）`refactor:` commit，提交信息写清搬了哪些函数。
- 每阶段结束打一个 tag（如 `pre-refactor-db`、`post-refactor-commands`），方便对照与回滚。
- 用 `git diff --stat` 复核：纯搬移阶段的 diff 应当主要是"整块删除 + 整块新增"，如果某个提交里出现大量零散小改动，说明混入了行为变更，需要停下来检查。

## 6. 重构会优化应用性能吗？——诚实评估

**结论先行：文件拆分本身几乎不带来运行时性能提升，它的主要收益是工程层面的；但拆分过程中附带两个真实的性能/体验机会。**

### 6.1 运行时性能：基本不变（这是正常的）

- **Rust 侧**：同样的代码编译成同样的机器码，模块拆分不改变二进制行为，启动速度、命令响应速度不会有可感知差异。
- **前端侧**：Tauri 的前端资源从本地磁盘加载，包体总共一百多 KB，模块数量变化对加载时间的影响在毫秒级以下，用户无感。

如果有人承诺"拆完文件应用就快了"，那是不诚实的。

### 6.2 开发体验：有真实提升

- **Vite HMR**：现在改 `App.tsx` 任何一行，整个千行组件模块都要重新执行；拆分后 HMR 失效范围缩小到单个子组件，热更新更快。
- **Rust 增量编译**：单文件改动触发整文件重编译，58KB 的 `main.rs` 拆成十个百行级文件后，增量编译命中粒度更细。
- **IDE 响应**：千行级文件在编辑器里的跳转、补全、搜索都会变快。

### 6.3 附带机会一：渲染范围优化（阶段 5 顺手可做）

`App.tsx` 目前 28 个 `useState` 全部平铺在顶层组件：任何状态变化（哪怕只是打开一个右键菜单）都会触发整棵组件树重新渲染。拆分组件时把局部状态（`contextMenu`、`colorPicker`、`sortMenuOpen`、拖拽临时状态）下沉到子组件后，这些高频交互的渲染范围会显著缩小。

注意：这属于"状态管理重组"带来的收益，是拆分过程中的主动设计，不是拆分文件的自动结果。如果只是把 JSX 搬走、状态全留在父组件，渲染次数一次都不会少。

### 6.4 附带机会二：真正的运行时性能瓶颈另有其处

与文件拆分无关、但调研中观察到的真实优化点，记录备查：

- `get_all_timeline` / `get_notes` 是全量加载，时间轴目前靠前端分页。便签量上千后应改为后端 `LIMIT/OFFSET` 或游标分页。
- 每次便签保存触发时间轴快照写入（`snapshot_json`），高频编辑时可考虑合并写入。

这两项建议在同步功能落地后、数据量实际增长时再处理，现阶段属于过度优化。

## 7. 风险与应对

| 风险 | 等级 | 应对 |
|---|---|---|
| `migrate` 逻辑搬移出错破坏用户数据 | 高 | 阶段 0 备份数据文件；阶段 1 后必做 5.3 数据验证；`migrate` 函数体原样搬移不改动 |
| 与云同步开发时间窗冲突 | 高 | 本方案特意排在同步开发之前；若同步已开工，则只做阶段 1–2（后端），前端暂缓 |
| `App.tsx` 状态耦合导致行为漂移 | 中 | 放在最后；一次只抽一个组件；局部状态下沉、全局状态保留；每步独立 commit 可回滚 |
| 防抖保存时序在抽 hook 后出错 | 中 | 阶段 3 重点回归"编辑→快速关窗"路径（清单 #19） |
| 重构范围蔓延（顺手改逻辑） | 中 | 原则 1 红线 + 5.6 的 diff 形态检查 |

## 8. 验收标准

全部阶段完成后，同时满足以下条件视为重构成功：

1. 四个巨型文件全部消失，最大单文件 ≤400 行。
2. `npm run build`、`cargo clippy`、`npm run lint` 全绿。
3. 5.2 契约比对零差异（命令清单、invoke 清单与基线一致）。
4. 5.4 回归清单 30 项全部通过。
5. 用重构前的 SQLite 数据启动，数据完整、迁移幂等。
6. 新增的 `db` 层单元测试全部通过。
7. git 历史中每个阶段可独立回滚，无行为变更混入。
