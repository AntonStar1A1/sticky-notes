## 第一轮：范围和边界

**Q1: "简单同步"到底多简单？**

你说"登录 + 简单同步"，但同步是个深坑。具体来说：

- 首次登录时，本地已有便签，云端是空的 → 全量上传？
答：全量上传
- 首次登录时，云端已有便签（另一台设备同步过），本地是空的 → 全量下载？
答：全量下载
- 首次登录时，两边都有便签 → 合并？冲突怎么办？
答：合并，每个设备可以生成一个唯一的uuid，可以以这个uuid+单个便签的id来，这样就不会冲突了吧。
- "简单同步"是指不做冲突处理（直接覆盖），还是做最基本的 Last Write Wins？
答： Last Write Wins，但是我不确定这个是什么意思，需要你和我解释

**Q2: 离线队列持久化的边界？**

- 用户在本地模式下创建了 100 条便签，然后登录 → 这 100 条全量上传算不算"离线队列"？
- 还是说"离线队列"只处理登录后的增量变更？
- 如果用户登录后断网操作了 50 条，再联网 → 这 50 条走队列，但之前本地的 100 条走什么逻辑？
答：算"离线队列"，登陆前的也处理

**Q3: 同步状态指示器显示什么？**

- 仅显示"同步中/已同步/离线"，还是需要显示"待同步 X 条"？
- 需要显示上次同步时间吗？
- 同步失败时怎么提示？重试按钮？还是自动重试？
答：仅显示"同步中/已同步/离线"，需要显示上次同步时间，自动重试。

## 我的判断

这个 MVP 方案**大方向没问题**，但有几个点需要你明确：

| 问题 | 建议 |
|------|------|
| Q1 同步复杂度 | MVP 做 Last Write Wins，不处理冲突，记录日志留后手 |
| Q4 表结构 | 本地 SQLite 统一用 UUID + `user_id` 字段（本地模式填 null） |
| Q5 Token 持久化 | Tauri 安全存储，MVP 不做刷新，过期重新登录 |
| Q8 退出登录 | 保留本地数据，登录不同账号时按 `user_id` 隔离 |
| Q10 后端改动 | 最小化，只加便签表和 API，不动现有用户系统 |
